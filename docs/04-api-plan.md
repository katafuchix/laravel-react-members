# 会員 API の計画（アプリ連携）

アプリ（Swift、Flutter など）から、会員の登録、認証、ログイン、ログアウト、編集、退会を使えるようにする計画。
**同じ Laravel プロジェクトに追加する**（別プロジェクトにはしない）。同じ `users` テーブルを、Web、管理画面、アプリで共有する。

## 現状（確認済み）

| 項目                   | 状態                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------- |
| `routes/api.php`       | なし                                                                                  |
| Laravel Sanctum        | 未導入                                                                                |
| `app/Http/Resources/`  | なし                                                                                  |
| API 用の例外の JSON 化 | 済み（`bootstrap/app.php` で `api/*` は JSON を返す設定）                             |
| 認証ガード             | `web`（User）、`admin`（Admin）。API 用は未定義                                       |
| 会員のメール認証       | `User` が `MustVerifyEmail` を実装。認証リンクは Web 用（セッションのログインが前提） |

## 方針

| 項目       | 決定（案）                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------------- |
| 場所       | 同じプロジェクト。`routes/api.php`、`app/Http/Controllers/Api/V1/`                             |
| 認証方式   | Laravel Sanctum のパーソナルアクセストークン（アプリ向け。Cookie やセッションは使わない）      |
| バージョン | `/api/v1/...`                                                                                  |
| レスポンス | Eloquent API リソース（`UserResource`）で整形。パスワード等は返さない                          |
| 対象       | 会員（`User`）のみ。管理者（`Admin`）は対象外                                                  |
| Fortify    | API では使わない（Web のセッション向けのため）。専用のコントローラーとフォームリクエストを書く |
| テスト     | PHPUnit のフィーチャーテスト。既存の CI で確認する                                             |

## エンドポイント（案）

| 機能             | メソッドとパス                         | 認証 | 内容                                                                                                |
| ---------------- | -------------------------------------- | ---- | --------------------------------------------------------------------------------------------------- |
| 会員登録         | `POST /api/v1/register`                | 不要 | 名前、メール、パスワード、確認用パスワード、`device_name`。作成してトークンを返し、認証メールを送る |
| ログイン         | `POST /api/v1/login`                   | 不要 | メール、パスワード、`device_name`。トークンを返す                                                   |
| ログアウト       | `POST /api/v1/logout`                  | 必要 | 今のトークンだけ削除する                                                                            |
| 自分の情報の取得 | `GET /api/v1/me`                       | 必要 | 名前、メール、認証状態                                                                              |
| プロフィール変更 | `PATCH /api/v1/me`                     | 必要 | 名前、メール。メールを変えると未認証に戻り、認証メールを再送する                                    |
| パスワード変更   | `PUT /api/v1/me/password`              | 必要 | 現在のパスワード、新しいパスワード。1分6回まで（Web と同じ）                                        |
| 退会             | `DELETE /api/v1/me`                    | 必要 | パスワードの再入力が必要。会員とすべてのトークンを削除する                                          |
| 認証コードの検証 | `POST /api/v1/email/verify`            | 必要 | メールの6桁のコードを送り、`email_verified_at` を記録する（方式A）                                  |
| 認証メールの再送 | `POST /api/v1/email/resend`            | 必要 | 新しいコードを送る。認証済みなら何もしない                                                          |
| 認証リンク       | `GET /api/v1/email/verify/{id}/{hash}` | 署名 | メールのリンクをブラウザで開くと認証して「完了しました」を表示する（方式C）                         |

- ログイン、登録のレスポンス例: `{ "token": "…", "user": { "id", "name", "email", "email_verified_at" } }`
- エラーは、検証エラーが `422`、未認証が `401`、権限なしが `403`（Laravel の標準の JSON）。

## 決めておくこと

| #   | 論点                                     | 推奨                                                                                                                                                                                                                                |
| --- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 2要素認証を有効にした会員の API ログイン | **フェーズ1では拒否する（`403`、Web で利用してもらう）**。許可すると 2要素認証を回避できてしまう。フェーズ2で、確認コードを受け取る方式を検討する                                                                                   |
| 2   | メール認証をアプリで必須にするか         | **フェーズ1では必須にしない**（認証状態は返すので、アプリ側で表示を切り替えられる）                                                                                                                                                 |
| 3   | メール認証の方式                         | **A（認証コード）と C（署名付きリンク）を両立する。** 1通のメールにコードとリンクを入れ、どちらで認証しても同じ `email_verified_at` に記録する。**先に A（API5）、後から C（API5b）**。C ができるまでは、メールにコードだけを入れる |
| 4   | パスワードリセット                       | フェーズ2。既存の Web のリセット画面にメールのリンクが届く方式なら、ほぼ追加実装なしで使える                                                                                                                                        |
| 5   | トークンの有効期限                       | フェーズ1は無期限（端末ごとに発行し、ログアウトで削除）。必要なら `config/sanctum.php` の `expiration` で期限を設ける                                                                                                               |
| 6   | 依存の追加                               | `laravel/sanctum` を追加する（`php artisan install:api`）。プロジェクトの規約で依存の追加は承認制のため、**実装前に承認が必要**                                                                                                     |
| 7   | API の仕様書                             | フェーズ1では、この md にまとめる。OpenAPI などは必要になってから                                                                                                                                                                   |

## メール認証の設計（方式A + 方式C）

- 認証の結果は、どちらの方式でも `users.email_verified_at` に記録する。先に成功した方で認証済みになり、もう一方は「すでに認証済み」として扱う。
- コードは `email_verification_codes` テーブル（新規）にハッシュで保存する。有効期限は10分、失敗は5回まで。再送すると古いコードは無効になる。
- API 経由の登録、メール変更のときは、Laravel 標準の `VerifyEmail` ではなく、コード入りの専用の通知を送る。Web から登録した会員は、今までどおり Fortify の標準のリンクで認証する（影響なし）。
- 方式C のリンクは署名付き URL で、セッションのログインを必要としない。開くと認証して「認証が完了しました。アプリに戻ってください」を表示する。

## ログイン試行の制限

- 管理者のログインと同じ考え方で、メールと IP の組み合わせごとに、1分5回まで。
- 上限に達したら `422`（`auth.throttle` のメッセージ）。
- ほかの API には Laravel 標準のレート制限（`throttle:api`）をかける。

## セキュリティ上の注意

- トークンは、発行時のレスポンスでしか平文で見られない（DB にはハッシュで保存される）。ログに出さない。
- パスワードは、既存の `Password::defaults()` の強度ルールを使う（本番は12文字以上、大小文字・数字・記号、漏えい済みは不可）。
- 退会は、パスワードの再入力を必須にする。
- HTTPS 以外では運用しない（本番）。
- ユーザーの列挙を避けるため、ログイン失敗のメッセージは「メールが無い」「パスワードが違う」を区別しない。

| 操作 | リクエスト                        | 成功時 | 失敗時                                                                                |

- 会員と、**すべての端末のトークン**を削除する（`personal_access_tokens` は外部キーの連動削除がないため、明示的に削除している）。パスキーは外部キーで一緒に消える。
- 削除と同じトランザクションなので、途中で失敗しても、トークンだけが消えた状態にならない。
- 退会後は、同じトークンも、同じメールとパスワードでのログインも使えない（`401`、`422`）。
- 同じメールで、あらためて登録し直すことはできる。

- PHPUnit は113件（105件 + 新規8件）が通過。Pint、PHPStan、`npm run check` も通過。

### 動作

| 操作         | リクエスト                            | 成功時              | 失敗時                                                                             |
| ------------ | ------------------------------------- | ------------------- | ---------------------------------------------------------------------------------- |
| コードの検証 | `POST /api/v1/email/verify`（`code`） | `200`、更新後の会員 | `401`、`422`（無効、期限切れ、誤り、失敗が多すぎる、形式が不正）、`429`（10回/分） |
| コードの再送 | `POST /api/v1/email/resend`           | `204`               | `401`、`429`（3回/分）                                                             |

- **コードの発行**: 6桁の数字。登録時、メール変更時、再送時に発行する。再送すると古いコードは使えなくなり、失敗の回数も0に戻る。
- **有効期限と回数**: 10分。1つのコードに対して、5回間違えるとロックされ（正しいコードでも拒否）、再送が必要。
- **メールとの紐づけ**: コードは、発行したときのメールアドレスと一緒に保存する。メールを変更すると、古いコードでは認証できない。
- **認証済みの会員**: 検証は、そのまま `200` で会員を返す。再送は何もせず `204`。
- **標準の認証メール**（リンクだけ）は送らない（`Registered` イベントを発行しない）。
- **認証の結果**: `email_verified_at` を記録し、`Verified` イベントを発行する。コードの行は削除する。
- 通知はキューで送る。送信に失敗しても、登録やメール変更は失敗しない（再送できる）。
- 退会すると、コードも一緒に削除される（外部キーの連動削除）。
